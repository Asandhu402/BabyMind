# Native workspace broker: approval and process-isolation protocol

**Status: design only. No broker executable, native confirmation UI, approval-token engine, AppContainer launcher, or IPC endpoint is implemented. Workspace actions remain disabled.**

This document is a security contract for the next implementation phase. It is deliberately stricter than the current in-process DLL and ctypes adapter. The DLL must not be treated as a broker process.

## 1. Security boundary

The model, renderer/UI, Python server, request JSON, and proposed path/content are untrusted. The broker is a separate Windows process running in a dedicated AppContainer identity with no network capabilities. It is the only component permitted to open workspace paths and perform the narrow native operations.

The parent process may request an operation, but it cannot approve it on the user's behalf. The broker itself must display a native confirmation dialog containing the exact operation, workspace, relative path, byte count, and (for new content) a digest/preview. The broker proceeds only after a direct affirmative action in that dialog. Closing the dialog, timeout, malformed IPC, or any error means deny.

The broker must not accept an "approved": true field, a caller-generated hash, or an approval token generated by Python as proof of consent.

## 2. Process creation and isolation

- Install/package a separately versioned broker executable; verify its expected publisher/signature and package hash before launch.
- Create or reuse a dedicated AppContainer profile for BabyMind. Grant its SID only the minimum required access to the selected workspace root and descendants; do not grant access to the user's profile, application secrets, browser data, or unrelated folders.
- Launch with STARTUPINFOEX and PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES, an explicit handle-inheritance list, and no internet/client/server capabilities. Fail closed if AppContainer creation or launch is unavailable.
- Place the process in a Job Object with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE, memory/CPU/process-count limits, and no breakaway. Apply available process mitigations (child-process creation disabled, extension points disabled, dynamic code prohibited where compatible).
- Pass only the minimum IPC handles. Use anonymous pipes or another per-launch channel whose handles are inherited only by the intended child. Do not expose a broad same-user named pipe that any process can connect to.
- Do not grant the broker arbitrary shell, process-launch, browser, network, or general filesystem capabilities. The broker accepts only the three fixed operation codes below.
- The broker independently opens and validates the selected workspace root. It must not trust a caller-supplied root handle or pre-resolved path as authorization.
- If the OS cannot establish the AppContainer identity and workspace ACL safely, refuse to start. Never fall back to an ordinary same-user child process and call it a sandbox.

The workspace ACL change must be explicit and reversible. BabyMind must show which directory is being granted to its AppContainer SID, preserve existing ACL entries, and remove only the exact ACE it added when access is revoked. No recursive permission broadening outside the selected workspace.

## 3. IPC framing and validation

Use a length-prefixed binary protocol, not ad-hoc JSON parsing in the privileged/native component.

Every frame contains:
- 32-bit protocol version (initially 1)
- 32-bit operation code
- 32-bit total frame length
- 128-bit request identifier generated by the parent (correlation only; not an authorization secret)
- bounded UTF-16 relative path length and path bytes
- operation-specific bounded fields

Reject unknown versions/codes, truncated frames, trailing bytes, duplicate fields, invalid UTF-16, embedded NUL, absolute/UNC/device paths, ADS syntax, traversal, reserved device names, lengths over the documented limits, integer overflow, and messages larger than 1 MiB. Read exactly one request per broker process. The broker sends one bounded structured result and exits. No request chaining or persistent command channel.

Allowed operation codes:
1. LIST_DIRECTORY: one non-recursive directory, at most 200 entries; names and basic types only.
2. READ_TEXT: one regular UTF-8 text file, maximum 32 KiB for the first release.
3. CREATE_NEW_TEXT: one new UTF-8 text file, maximum 32 KiB; exclusive create, never overwrite.

Do not expose edit, delete, recursive search, arbitrary command execution, process launch, or project test execution through this protocol.

## 4. Native approval and one-use execution

Approval is an internal broker state transition, not a caller-supplied token.

1. Parse and validate the complete request; canonicalize the relative path.
2. Open and pin the workspace root and the relevant parent/target using the native handle-relative routines. Reject reparse points and unsupported filesystems.
3. Compute the operation binding inside the broker: protocol version, operation code, root volume/file identity, canonical relative path, target/parent file identity where applicable, exact byte limit, and SHA-256 of create content.
4. Display a broker-owned native confirmation dialog with human-readable details. For CREATE_NEW_TEXT, show the exact filename, byte count, and a bounded content preview plus digest. For reads, state that the file contents will be sent to the local model/UI.
5. On affirmative user input, create an in-memory approval record with a cryptographically random 256-bit nonce, a monotonic-clock expiry no later than 60 seconds, and the full operation binding. The nonce never leaves the broker and is not accepted from the parent.
6. Atomically mark the record consumed immediately before the operation. The broker permits one execution only. Expired, mismatched, duplicate, cancelled, or already-consumed records are denied.
7. Revalidate the pinned handle identity and operation limits immediately before use. Perform the operation through the same pinned handles; never reopen a target by an untrusted path after approval.
8. Destroy the record and sensitive buffers on success or failure. Do not log file contents, approval material, or secrets.

Because the first implementation performs confirmation and execution in one short-lived broker process, no reusable approval token needs to be persisted or exposed to Python. If a future UI requires a two-phase flow, it must use a broker-owned challenge with the same binding, nonce, monotonic expiry, and atomic consume semantics; the Python/UI confirmation flag is never authoritative.

## 5. Operation-specific invariants

### LIST_DIRECTORY
- Pin the selected directory handle before confirmation.
- Enumerate that one directory only; never recurse or follow reparse points.
- Cap returned entries at 200 and return an explicit truncation flag.
- Do not return file contents, alternate data streams, or absolute paths.

### READ_TEXT
- Pin the exact file handle before confirmation.
- Require a regular non-reparse file and a size no greater than 32 KiB.
- Read at most 32 KiB plus one byte to detect growth; reject if the extra byte exists.
- Require strict UTF-8 and reject embedded NUL/binary data.
- Return contents only after the native dialog clearly tells the user that the selected text will be read by BabyMind.

### CREATE_NEW_TEXT
- Pin and verify the parent directory handle before confirmation.
- Bind the exact filename, content digest, and byte count.
- Use native exclusive creation relative to the pinned parent handle. Never overwrite, truncate, or replace.
- On a partial write or flush failure, remove only the file created by this request using its still-open handle/identity; do not delete a replacement path.

## 6. Required tests before integration

- AppContainer profile creation, ACL grant/revoke, and failure recovery.
- Confirm that no network capability is present and outbound network access fails.
- Verify inherited handles are exactly the allowlist and unrelated handles are not inherited.
- Verify child-process creation, process breakaway, and arbitrary executable launch are blocked.
- Attempt pipe/IPC access from a second same-user process; it must have no usable broker channel.
- Reject malformed/truncated/oversized IPC frames and all unknown operation codes.
- Cancel/close/timeout the native dialog; verify no side effect.
- Replay, duplicate, alter, expire, and cross-bind request identifiers and internal approval records; all must fail.
- Race rename/replacement/reparse-point swaps against root, parent, and target handles with deterministic barriers.
- Verify file growth, invalid UTF-8, binary data, oversized content, partial writes, concurrent create, and existing-target behavior.
- Verify process crash/kill at every operation phase leaves no unintended file or permission changes.
- Run on every supported Windows version and supported local filesystem. Network shares and non-NTFS volumes remain unsupported unless separately reviewed.

## 7. Enablement gates

Do not connect the ctypes adapter to HTTP routes or set WORKSPACE_FILE_ACTIONS_ENABLED = True until:
- The broker executable and AppContainer launcher are implemented.
- Native confirmation is broker-owned and approval is consumed exactly once.
- The broker protocol and all adversarial tests pass on Windows CI.
- ACL grant/revoke and packaging integrity are reviewed.
- An independent Windows security review signs off on the threat model and implementation.
- User-facing capability descriptions match the exact tested operations.

Project test execution is a separate feature. It requires its own OS-enforced sandbox, process policy, filesystem/network policy, resource limits, and independent review. The workspace broker must never run tests or commands.
